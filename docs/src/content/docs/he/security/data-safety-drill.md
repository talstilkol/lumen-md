התרגיל בודק את ההבטחה שפתק אף פעם לא נשמר בחצי. הוא מעביר **כל דרך שבה Lumen כותב
פתק לתיקייה** דרך ארבעה סוגי תקלות, על דיסק אמיתי עם תהליכים אמיתיים:

| תקלה | מה קורה |
|---|---|
| **kill -9** | תהליך שומר פתקים הכי מהר שהוא יכול, ונהרג ב-`SIGKILL` ברגע אקראי, 1,000 פעמים |
| **דיסק מלא** | פתק גדל עד ששמירה כבר לא נכנסת למערכת קבצים קטנה (`ENOSPC`) |
| **אובדן הרשאה** | התיקייה והפתקים הופכים לקריאה בלבד באמצע השמירה |
| **תוכנה אחרת** | עורך או לקוח סנכרון שומרים את אותם פתקים (קובץ זמני ואז שינוי שם) בזמן ש-Lumen שומר |

כל גרסה שנשמרת נושאת SHA-256 של הטקסט שלה. אחרי כל סבב, כל פתק חייב להיות **גרסה
אחת שלמה**, לא ישנה יותר מקודם, ועדיין קיים. שמירה שנכשלת חייבת להיכשל בקול, כדי
שהאפליקציה תשמור את הטקסט ותנסה שוב.

התרגיל בודק את התיקייה בטלפון (`src/storage/vault/mobile.ts`, הקוד האמיתי), את
ה-worker של OPFS ש-Safari לפני 26 משתמש בו, את הכתיבה של אפליקציית המחשב
ב-`src-tauri/vault/src/lib.rs` (האלגוריתם; ‏`cargo test` בודק את קוד ה-Rust עצמו), ואת
השמירה האטומית של משימה W1.5 כשהיא נמצאת בענף. המסלול של File System Access
בדפדפן אטומי מעצם התכנון, ומטריצת ה-e2e ‏(`e2e/data-safety.spec.ts`) מכסה אותו.

## הרצה

```sh
npm run drill:data-safety -- --kills 1000 --full-disk /mnt/small
```

`--full-disk` מקבל מערכת קבצים קטנה שהרכבתם לבדיקה (בלינוקס:
`sudo mount -t tmpfs -o size=256k tmpfs /mnt/small`). בלי זה, חלק הדיסק המלא מדולג.
כשמריצים כ-root, התהליך ששומר עובר למשתמש בלי הרשאות, כדי שבדיקת ההרשאות תהיה
אמיתית.

הדוח נכתב ל-`reports/data-safety-drill-<commit>.md` ול-`.json`, אחד לכל גרסה. קוד
היציאה הוא 0 רק כשאף פתק לא נפגע ולא אבד.
