את סטי הפיתוח ואת ה-probes של Lumen כותבים אותם סוכנים שכותבים את הקוד, ולכן
הם נוטים לעבור: HeQ dev כבר ב-1.0 ולא מבדיל בין גרסאות. הסטים המוחזקים הם
הבדיקה שהכותבים לא יכולים לכוונן אליה. `npm run heldout` הוא המעריך שלהם.

## מה מוחזק

| סט | פריטים | מה נמדד | מקור | רישיון |
|---|---|---|---|---|
| `qa-he` | 300 | שאלות ותשובות בעברית בלי הקשר: תשובה קצרה שתואמת תשובת ייחוס או כינוי שלה | MKQA ‏(Apple), תשובות בעברית ובאנגלית | CC BY-SA 3.0 |
| `ocr-he` | 120 | CER של OCR, נקי ומושפל, ב-4 גופנים שסט ה-OCR הזהוב לא משתמש בהם | שאלות MKQA בעברית, מרונדרות; גופני Fontsource | CC BY-SA 3.0 (הטקסט); הגופנים OFL 1.1, לא מופצים |
| `asr-he` | 200 | WER ו-CER של הכתבה | FLEURS he_il, פיצול ה-**train** (הריפו דוגם רק את validation ואת test) | CC BY 4.0 |

אף אחד מהמאגרים האלה לא משמש בריפו כסט פיתוח, כסט זהוב או כ-probe. בדיקה
(`src/__tests__/heldout.test.ts`) מוודאת את זה.

## איך הפריטים נשארים מוסתרים

- **אילו פריטים** יש בסט נקבע ב-HMAC עם הסוד של המעריך. המאגרים ציבוריים,
  אבל בלי המפתח אי אפשר לדעת אילו מהפריטים שלהם מוחזקים.
- **הפריטים** קיימים רק בחבילות שמוצפנות למפתח של המעריך (X25519,
  ‏HKDF-SHA256, ‏ChaCha20-Poly1305), ב-`~/.cache/lumen-heldout` או
  ב-`$LUMEN_HELDOUT_DIR`, ואף פעם לא בריפו.
- **המפתח** מגיע מטל או מהמארח הלילי בזמן הריצה (`LUMEN_HELDOUT_KEY` או
  `--key-file`). קובץ מפתח בתוך הריפו נדחה.
- **בריפו** יש רק את `eval/heldout/manifest.json` (מקורות, גדלים, רישיונות,
  canary אחד לכל סט, והחותם של כל סט) ואת `eval/heldout/commitments/`
  (גיבובים של הפריטים עם מפתח).
- **הפלט** הוא מספרים מצטברים. מזהי פריטים בו הם גיבובים עם מפתח. שמע
  ותמונות נכתבים לתיקייה זמנית מחוץ לריפו ונמחקים אחרי מתן הציון.

## פקודות

```sh
npm run heldout -- status                       # בלי מפתח
npm run heldout -- keygen                       # הבעלים או המארח הלילי, פעם אחת
npm run heldout -- build --record               # הורדת המאגרים, הגרלה, הצפנה ורישום החותמים
npm run heldout -- run --models qwen2.5:7b,gemma3:12b --asr-model <dir>
npm run heldout -- scan --require-key --prs open
npm run heldout -- log --verify
npm run heldout -- export --to <run recipient> --out <file>   # עותק לריצה אחת על GPU בענן
```

`export` מצפין מחדש את הסטים למפתח שנוצר לריצה אחת של
[models:cloud](/he/ai/models-cloud/). העותק יכול לתת ציון, אבל לא לבנות
ולא לייצא, ואין בו שום חלק מהמפתח של המעריך.

`build` צריך Python 3 עם `pip install -r scripts/golden/requirements.txt`
וגישה ל-Hugging Face, ל-GitHub ול-npm. הוא בודק שוב כל רישיון במקור, ונעצר
אם יש אי-התאמה.

## בדיקת הזיהום

`npm run heldout -- scan` קורא כל קובץ ש-git עוקב אחריו (ואת הקבצים שלא
במעקב ולא מוחרגים). הוא יכול לקרוא גם את השורות שנוספו ב-diff
(`--diff <rev>`), את ה-diff ואת הגוף של PR-ים (`--prs 443,449` או
`--prs open`), ותיקיות נוספות (`--paths`). הוא מסמן:

- canary של כל סט, וזה עובד גם בלי המפתח;
- את המפתח של המעריך;
- עם המפתח, כל פריט מוחזק: רצף אחד של 13 מילים ממנו, חצי מרצפי 8 המילים שלו
  במסמך אחד, או פריט קצר בשלמותו. ניקוד, פיסוק ושבירת שורות לא מסתירים
  העתקה.

הוא יוצא עם 1 על כל ממצא. `models:day` מריץ אותו לפני מתן הציון.

## גרסאות והחלפה

לכל סט יש גרסה, וכל דוח מציין את הגרסאות ואת ה-digest שבהם השתמש. בכל רבעון,
`build --rotate --record` מחליף 20% מכל סט בפריטים שאף גרסה לא השתמשה בהם.

## היומן

כל בנייה וכל בקשת ציון נרשמות ב-`log.jsonl` ליד החבילות: מי ביקש, מתי, על
איזה commit ואילו גרסאות, וה-hash של התוצאה. כל רשומה נושאת את ה-hash של
הרשומה שלפניה, ולכן `log --verify` תופס רשומה שנערכה או נמחקה. כל קובץ
תוצאות נושא גם את רשומת היומן שלו.

## ב-models:day

כשהמפתח של המעריך נמצא, `npm run models:day` מוסיף את שלב `heldout`. הוא
מוריד את מודל ההכתבה, בונה את החבילות אם הן חסרות, מריץ את הסריקה, ואז
נותן ציון לכל ששת הסטים על `qwen2.5:7b` ועל `gemma3:12b`. בלי המפתח, השלב
מסומן כחסום.
