אפליקציית שולחן העבודה (Windows, macOS, Linux) מתעדכנת מהגרסאות שמתפרסמות
ב-GitHub של הפרויקט.

- **בדיקה:** לוח הפקודות ← **בדיקת עדכונים…**. גרסה יציבה לא בודקת מעצמה.
  גרסת בטא בודקת פעם ביום בהפעלה, אלא אם מכבים את זה ב[דגלי הפיצ'רים](/he/getting-started/beta/).
- **ערוץ:** לוח הפקודות ← **ערוץ עדכונים** עובר בין גרסאות יציבות לגרסאות
  בטא ([ערוץ הבטא](/he/getting-started/beta/)).
- **מה נשלח:** בקשה אחת לשרת הגרסאות, עם מספר הגרסה והפלטפורמה. בלי פתקים,
  בלי חשבון ובלי מזהה. הבקשה מופיעה ביומן הפרטיות.
- **מקומי בלבד:** כשמדיניות הפרטיות היא *מקומי בלבד*, לא נבדק כלום, והפקודה
  אומרת זאת.
- **אימות:** כל עדכון חתום. האפליקציה בודקת את החתימה מול המפתח שמובנה בה,
  ודוחה קובץ שאינו תואם, או גרסה ישנה שמוצגת כחדשה.
- **התקנה:** אחרי האישור שלכם, ‏Lumen מוריד, מאמת, מתקין ומופעל מחדש.

לגרסה שנבנתה בלי מפתח העדכונים (בנייה מקומית או גרסת פיתוח) אין מנגנון
עדכון. *בדיקת עדכונים…* אומרת שהוא לא מוגדר, ומתקינים גרסאות חדשות ידנית.

## מתקינים חתומים

המתקינים של הגרסאות ייחתמו כשתעודות החתימה של הפרויקט יהיו מוכנות
(Windows Authenticode, ‏Apple Developer ID). עד אז Windows SmartScreen
ו-macOS Gatekeeper מציגים אזהרה בהפעלה הראשונה.

**‏Windows: ‏SignPath Foundation (משימה W11.S15).** ‏Smart App Control חוסם
אפליקציות לא חתומות, ושירות Artifact Signing של Microsoft לא פתוח לאדם
פרטי בישראל. ‏SignPath Foundation חותמת בחינם, בתעודה שלה, על פרויקטי קוד
פתוח ברישיון שאושר ב-OSI. ‏Lumen ברישיון MIT, שאושר ב-OSI. לא צריך תעודת
EV. הבקשה היא צעד של הבעלים (W11.O1).

- ‏`npm run release` מעביר ל-Tauri את SignPath בתור ה-`signCommand` של
  Windows (‏`scripts/windows/signpath-sign.mjs`), כשארבעת ערכי `SIGNPATH_*`
  מוגדרים. כל בקשת חתימה מחכה אז לאישור שלה ב-SignPath.
- אחרי הבנייה, כל מתקין של Windows נבדק (‏`scripts/windows/verify-signature.mjs`):
  חייבת להיות בו חתימת Authenticode, וב-Windows גם `signtool verify /pa`
  צריך לקבל אותה.
- ‏`release/signing.json` אומר "Windows: חתום" רק כששני התנאים מתקיימים.
  בלי פרטי SignPath הגרסה יוצאת עם מתקין לא חתום, והרשומה אומרת את זה.

כל אחד יכול לבדוק מתקין:

```bash
node scripts/windows/verify-signature.mjs Lumen_<version>_x64-setup.exe   # יציאה 1 כשהוא לא חתום
signtool verify /pa /v Lumen_<version>_x64-setup.exe                      # ב-Windows
```

## מה מותר לאפליקציה

לחלון אין הרשאה כללית למערכת הקבצים. הוא ניגש רק לתיקיית הכספת שבחרתם, דרך
הפקודות של Lumen עצמו. אין גישה לשורת הפקודה, אין HTTP חופשי מהצד הנייטיב,
ואין source maps בקבצים שמופצים.

**מה כתוב, ומה עוד לא מופעל (משימה W11.S18):**

- כל קובץ capability אמור להתאים לתמונת מצב שנבדקה
  (‏`security/tauri-capabilities.snapshot.json`), ו-capability שנותן לחלון
  הרשאה של עדכונים, שורת פקודה, מערכת קבצים, תהליכים, HTTP או פתיחת קישורים
  אמור להיכשל בבדיקה. הבדיקה היא בדיקת יחידה
  (‏`src/__tests__/tauriIsolation.test.ts`) שמריצים ביד: עדיין אין CI שמריץ
  אותה בכל שינוי. **היום היא אדומה**: ה-capability הראשי השתנה (הרשאת קיצור
  מקשים גלובלי) ותמונת המצב שלו לא נבדקה מחדש. הבעלים בודק אותו ומעדכן את
  תמונת המצב.
- **אפליקציית בידוד** (‏`src-tauri/isolation/`) כתובה כדי לבדוק כל הודעה
  מהחלון לפני שהיא מגיעה לצד הנייטיב, כחומה שנייה מאחורי ה-capability: רק
  הפקודות של Lumen עצמו, נתיב בכספת רק בתוך הכספת, ואף פעם לא פקודת עדכון או
  שורת פקודה. **היא לא מופעלת**: ‏`tauri.conf.json` לא משתמש בתבנית הבידוד.
  ברשימת הפקודות המותרות שלה חסרות גם שתי פקודות שנוספו לאפליקציה מאז,
  ‏`vault_write_if` ו-`vault_remove_if` (שמירה בהשוואה-והחלפה), כך שהפעלתה
  כמו שהיא הייתה שוברת את השמירה בשולחן העבודה. אותה בדיקה אדומה גם על זה.

עד שרשימת הפקודות מעודכנת, הבדיקה ירוקה והתבנית מופעלת
(‏`node scripts/tauri-isolation.mjs --enable`, שדורש גם עדכון תלויות עם גישה
לרשת), קובץ ה-capability הוא החומה היחידה.
