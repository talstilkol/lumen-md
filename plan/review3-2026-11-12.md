## Bottom line

**E2EE can't ship from these heads yet.** The work fixes most of what the first two reviews found, and fixes it well. One new **high** remains:

- **The finding (N1):** a device that opens with its own age key has no anchor bound to a secret. The provider can replace the whole keyring and manifest with ones it made. The device then syncs into that vault: the provider overwrites its notes and reads what it writes next. This holds even for a paired device.
- **The fix:** small, about 30 lines.
- **Release branch:** `chore/release-beta1` still contains the pre-fix keyring (RR-10). It must not ship as it is.
- **Two medium findings** (N2 and N3) leave a revocation silently undone in specific provider-malicious cases.

## New findings

### N1 — HIGH — device-key unlock has no cryptographic anchor; the provider substitutes the whole vault

- **Where:**
  - `src/sync/e2ee/engine.ts:246-259` (`unlockWithDevice`).
  - `src/sync/e2ee/keyring.ts:402-440` (`refreshKeys`), `:372-391` (`checkDescent`), `:226-228` (`keyringDigest`).
- **Scenario:** an enrolled device (paired or not) restarts. Keys live only in memory, so it opens with `unlockWithDevice` again; its persisted state keeps `ring` and `anchor`. The provider writes a keyring of its own:
  - the device's public recipient with an age wrap of a secret S' the provider chose;
  - sealed contents under S' with `older[0] = S0'` and `devices = {phone}`;
  - `parent` and `chain` set to the device's anchor `(epoch, rev, digest)`. The digest is a SHA-256 of public keyring fields, so the provider can compute it.
  - It also writes a manifest under S' with a higher counter and an empty history.

  What follows:
  - `unlockWithDevice` accepts it.
  - In `refreshKeys` the keys *are* the forged ones, so the "same keyring" or same-epoch branch runs. The lineage rule `older[myEpoch] == my secret` (`:432`) never runs.
  - `checkDescent` finds the anchor in the forged chain and returns "ok".
  - `checkFreshness` returns only "unproven" (freshness → unverified, no error).
- **Proof:** `rr3/n1-device-unlock-forgery.test.ts` (log in `rr3/n1.out`).
  - The test FAILs: `a.md on the phone: "text the provider chose"` and `provider reads new.md: "a note written after the restart"`, with the phone paired beforehand.
  - The control (the same forgery against a passphrase device) is refused with `DecryptError`, because the provider can't make a passphrase wrap.
- **Reach:** `unlockWithDevice` isn't exported from `index.ts`, and #291's session unlocks by passphrase only. Today this is reachable through the library API, which is documented in the engine (`access: {device, identity}`) and in spec §5/§9. It is the only way an enrolled device is used, so it becomes reachable as soon as device-key unlock is wired up.
- **Fix:**
  - Bind the anchor to a secret. Persist `ring.check = HMAC(epochKeys(S_epoch).keyring-derived anchor key, vaultId‖epoch‖rev‖digest)`, or simply `sha256("lumen-anchor"‖S_epoch)`, in `DeviceState`.
  - In `E2eeSync.refresh` (and in a `unlockWithDevice(provider, id, identity, state)` overload), before anything else:
    - at `keys.epoch === s.ring.epoch`, require the check to match `keys.secret`;
    - at a higher epoch, require it to match `keys.olderSecrets.get(s.ring.epoch)`;
    - at a lower epoch, it is a rollback.
  - Better still, make the chain entries MACs under the epoch's keyring key rather than public digests.
  - Correct spec §9.

### N2 — MEDIUM — a CAS-lying provider undoes a revocation; only the re-keyer notices, later

- **Where:**
  - `engine.ts:526-547`: the commit isn't read back.
  - `provider.ts:110-138`: `proveCas` probes a fixed, recognisable name, `lumen-e2ee-cas-probe`.
- **Scenario (a):** the same race as t8 "lie". A revokes the phone while B enrolls a laptop, and the provider drops If-Match on the keyring only.
  - A's `rekey()` returns `devices: []`, so the user is told the phone is out.
  - B's keyring wins, wrapped for `['phone', 'laptop']`.
  - A's next round gets `KeyringForkError`. B's next round is fine.
  - The revoked phone restarts, opens the live keyring and reads a note B wrote after the revocation.
- **Scenario (b), split view (inherent):** the provider keeps A on its own copy. No device ever errors. The only detector is a pairing code between the branches (`PairingEpochError`).
- **Proof:** `rr3/n2-cas-lie-scope.test.ts` (log in `rr3/n2.out`). (a) FAILs and (b) behaves as documented.
- **Fix:**
  - After the keyring PUT, read the keyring back and require its digest to equal the one just committed; throw before reporting success. This catches every non-split CAS failure immediately.
  - On `KeyringForkError` after a revocation, tell the user the revocation may not have taken effect and must be re-run from a verified device.
  - Document that `proveCas` detects misconfigured servers, not a malicious provider, which can special-case the probe name.
  - Spec §9 should say a revocation is only as current as the other devices' view: confirm it by pairing.

### N3 — MEDIUM — a pairing code issued before a revocation pairs a rolled-back device, which then re-keys for the revoked phone

- **Where:**
  - `pairing.ts:93-104`: the epoch check compares the code with the keys the provider showed.
  - `engine.ts:619-645`: `pair()`.
  - `PAIRING_TTL_MS = 15 min`.
- **Scenario:**
  1. A issues a code at epoch 1 for a laptop.
  2. Five minutes later A revokes the phone (epoch 2).
  3. The provider shows the laptop the epoch-1 keyring and manifest.
  4. The user enters the still-valid code. The epochs match, so pairing succeeds and the laptop is "paired".
  5. The laptop's `rekey()` wraps epoch 2' for `["phone"]`.
- **Proof:** `rr3/n3-pairing-window.test.ts` FAILs (log in `rr3/n3.out`): `pair: ok | laptop freshness: paired | laptop re-key: epoch 2, wraps ["phone"] | phone unwraps: true`.
- **Fix (any of these):**
  - Make pairing a two-way handshake: the new device shows a nonce, and the old device answers with its *current* anchor at answer time.
  - Have the issuing device refuse to re-key or revoke while it has an unexpired outstanding code (or show "cancel pairing first").
  - Make a paired device's first re-key or enroll require a code issued after its last observed epoch change.
  - At the very least, shorten the TTL and document the window.

### N4 — no finding — the reset path can't be used as a downgrade

`rr3/n4-reset-downgrade.test.ts` passes 2/2 (log in `rr3/n4.out`):
- A protocol-2 keyring relabelled as protocol 1 gives `DecryptError`, with or without the reset flag.
- An anchored device that the user reopens with the reset flag over a rolled-back keyring gets `KeyringRollbackError`.

A genuine protocol-1 keyring exists only in vaults that ran a pre-release build. Even there, a forced reset forks the vault into one that only passphrase holders can read, and they already hold everything. That is an availability issue, not a confidentiality one.

### N5 — LOW — the provider can make a device believe it was revoked

- **Where:** `keyring.ts:226-228` (the digest excludes the plaintext wraps); `engine.ts:249-256`; `keyring.ts:579`, where `pickWraps` keeps a swapped wrap.
- **Scenario:** the provider replaces device X's wrap with an age file of a random secret to X's public recipient.
  - X's next `unlockWithDevice` throws `RevokedError` ("This device was removed from the vault").
  - Because the digest excludes the wraps, this is no fork, and it survives enrollments until the next re-key.
  - It is a denial of service with a misleading message.
- **Basis:** reading; the mechanism is the same as N1's.
- **Fix:** distinguish "my wrap doesn't open to a secret that opens `sealed`" (`TamperedWrapError`, retry or ask the user) from "the sealed list doesn't list me" (`RevokedError`). Never act destructively on the first.

### N6 — LOW — unverified devices still write under a stale epoch (RR-5 residue, a policy choice)

- **Where:** `engine.ts:859-961`. `round()` pushes regardless of `freshness`.
- **Scenario:** lane K's k2/t5 (i). The note a fresh, unpaired laptop writes is readable by a phone revoked in an epoch the provider withholds.
- **Fix:**
  - At epoch ≥ 1 and while unverified, hold uploads (pull-only) until the device is paired or confirmed.
  - Or ask once before the first upload ("this device can't verify it has the latest keys").

### N7 — LOW — Drive create-only isn't atomic, and the probe can't see it

- **Where:** #291 `src/sync/e2ee/providers/gdrive.ts:131-168`.
- **Scenario:**
  - Two concurrent first re-keys at epoch 0 (or a re-key and an epoch-0 call-off) both create `lumen-e2ee-keyring`.
  - If Drive's listing lags, both "win".
  - The loser later gets `KeyringForkError` (loud). At epoch 0 there is no device wrap to leak, so this is availability only.
  - `checkConditionalWrites` tests create-only sequentially, so it passes.
- **Basis:** reading; the PR text already lists it as unmeasured on real Drive.
- **Fix:**
  - Serialise first-keyring creation through the header (If-Match on `lumen-e2ee-vault`), which Drive does support.
  - Or create the keyring at vault creation, so epoch 0 never needs create-only on the keyring.
