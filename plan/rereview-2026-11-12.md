The following were checked and found sound:
- **Nonces and keys:** there is no nonce or key reuse across epochs. Each epoch's keys come by HKDF from a fresh 32-byte secret, and every AES-GCM nonce is a random 96-bit value. The passphrase wrap key is reused across epochs, but always with a random nonce and the epoch in the AAD.
- **Keyring AAD:** it binds the protocol (1), vaultId, epoch and role.
- **Manifest and blob AAD:** it binds vaultId, kind and object name. The object name carries the epoch label, and the key is per epoch.
- **Frozen protocol:** `protocol: 2` sits inside the AEAD.
- **Keyring `header` field:** it is bound by a SHA-256 in the sealed part.
- **Carry check:** `resumeEpoch` carries only the exact frozen digest. A provider can't make a device accept a manifest it didn't commit, but holders of the epoch key (members, including a device about to be revoked) can.
- **Old passphrase:** it never reaches N+1.
- **#472 (7f0bfc789):** `unlock()` writes nothing now, and upgradeKdf is opt-in. That is correct for the at-rest vault.

## RR-1 (critical when a pre-fix keyring exists): the legacy path defeats the sealed device list

- **Where:**
  - `src/sync/e2ee/keyring.ts:311`: `enrolled = prior.devices ?? legacyDeviceList(current.file, prior)`.
  - `:231-246`: `legacyDeviceList` builds the list from the plaintext map. Its only filter on an entry is "the recipient parses, and the wrap starts with `age-encryption.org/v1\n-> X25519 `" (`:239`).
  - `:378`: `enrollDevice` uses the same fallback.
  - `:390-405`: `sealDeviceList` re-seals at the **same epoch**.
  - `:262`: `refreshKeys` returns early at an equal epoch, so nobody re-checks.
- **Attack (a), TOFU:** the provider adds `devices.evil = {recipient: <its key>, wrap: <any age file to its own key>}`. Building that wrap takes one `age -r` call, so the filter is cosmetic. The first fixed device seals `evil` in as a trusted member, and the next re-key wraps S_{N+1} for it. The attacker then reads `older` (every secret, S0 included), the manifest and all blobs.
- **Attack (b), downgrade after a *clean* migration:** the provider keeps the pre-migration keyring bytes. They are sealed under the current epoch key, and they have no `devices` field. After a trusted device has sealed the list, the provider serves those bytes again with `evil` added to the plaintext map. The epoch is equal, so no rollback check fires. `prepareEpoch` sees `prior.devices === undefined` and takes the legacy path again.
- **Test:** `rr12/t1-legacy-downgrade.test.ts`. The legacy vault is made by the real bb83b845a engine. Both cases FAIL: `re-key wrapped for: ['evil'] attacker reads: ['secret.md']`. Lane K's migration test only injects *invalid* junk and the *revoked* tablet, both of which the filter drops. It never injects a well-formed attacker entry, and never replays.
- **Scope:** the pre-fix keyring was never on `main`, but `origin/chore/release-beta1` contains d935906aa without a19436332 (RR-10). If beta1 ships before this PR, legacy vaults exist in the wild.
- **Fix:**
  - **Preferred:** since no pre-fix keyring build has been released, delete the legacy path. Refuse a keyring whose sealed part has no `devices` (`DecryptError("keyring from a pre-release build: re-create")`). In the same release, rebase or drop W1.7 from `chore/release-beta1`.
  - **If legacy support must stay:** migrate by **re-keying** to N+1, which is protected by the epoch monotonicity, not by a same-epoch re-seal. Show the plaintext list to the user for confirmation before sealing it, and once a device has seen a sealed list at epoch N, refuse a legacy keyring at N (persist `sealedAtEpoch`). In every case, see RR-2.

## RR-2 (high): an equal epoch number is taken as "same keyring"

- **Where:**
  - `src/sync/e2ee/keyring.ts:262`: `if (k.file.epoch === keys.epoch) return keys;`.
  - `engine.ts:319`: the only per-round keyring check.
- **Attack:** any second keyring at the same epoch goes unnoticed by devices already at that epoch, and is fully trusted by any code path that reads `current` afresh (`prepareEpoch`, `enrollDevice`, `sealDeviceList`). A provider can produce one by:
  - an older same-epoch version (RR-1b, or undoing an enrollment);
  - two re-keys racing, when the CAS isn't honoured (RR-8);
  - withholding, which forks devices onto two epoch-N+1 secrets with the same number.
- In RR-8, device A keeps using its own S2 while the stored keyring is B's S2'. The revocation A made is undone, and A sees nothing until a later manifest read fails with a generic `DecryptError`.
- **Test:** shown by RR-1b and RR-8.
- **Fix:**
  - **Same-epoch check:** on every refresh at an equal epoch, open `sealed` with `keys.keyring`. A failure means a keyring this device's secret didn't produce: raise `KeyringForkError`, not "same keys".
  - **Hash chain:** add `parent: sha256(previous keyring bytes)` and a same-epoch `rev` counter to the sealed contents. Make devices persist `(epoch, rev, digest)` and refuse a lower `rev` or a different digest at the same `rev`. This is the keyring analogue of the manifest's counter and history.

## RR-3 (medium): a revoked device can wedge the vault by planting the next manifest name

- **Where:**
  - `manifest.ts:81-87`: names are `HMAC(names, "manifest/<N>")`.
  - `keys.ts:120`: the names key is always derived from S0, which every device ever enrolled holds.
  - `engine.ts:454`: step 4 is create-only, and losing means "another device finished" → `readManifest`.
  - `engine.ts:337`: `resumeEpoch` skips whenever an object exists.
  - `engine.ts:612`: `openManifest` throws.
- **Attack:** a phone the user is about to revoke, or a thief holding it, still has the provider credentials. It writes random bytes at the names for `manifest/2…manifest/5`. Then:
  - The revocation re-key commits the keyring, fails step 4 and throws `DecryptError`.
  - From then on, every device's round throws `DecryptError: Unknown sealed-object format`.
  - Nothing recovers automatically. Lane K's own test at `e2eeRekeyIntegrity.test.ts:167-185` accepts a similar permanent wedge ("manifest is missing") when an epoch-N holder overwrites the frozen manifest before step 4.
- **Test:** `rr12/t3-preplant-manifest.test.ts` FAILs: `rekey: DecryptError | sync errors: A…, B…`.
- **Fix:**
  - Make the label unpredictable and per-secret, `manifest/<N>/<16 random bytes b64u>`, in the sealed `manifest` field (`isManifestLabel` changes accordingly).
  - **Write the new manifest before the keyring commit:** freeze → put `manifest/<N+1>/<rand>` (sealed with S_{N+1}, orphaned if the commit loses) → CAS the keyring. The keyring write is then truly the only commit point, step 4 and its carry gap disappear, and racing re-keyers can't collide.
  - Also, when the epoch's manifest exists but won't open under its key, treat it as junk and replace it with the carried successor using CAS on its etag. Only the epoch's members could have produced a valid one.

## RR-4 (medium): freeze TTL across clocks, and check-then-act around the commit

- **Where:**
  - `engine.ts:675`: the thaw compares the *reader's* clock with `frozen.at`, which is the re-keyer's clock.
  - `engine.ts:432-434`: the re-keyer's guard (re-read the frozen etag, and its own elapsed time under 5 minutes) runs *before* `put(KEYRING)`, not atomically with it.
  - `engine.ts:713-725`: the thawing device re-reads the keyring *after* its own write, then treats its commit as done and GCs the superseded blobs (`:737`).
- **Whose clock:** the 5-minute guard uses the re-keyer's own clock, as a difference, so it is immune to skew. It is not immune to a laptop suspend, an NTP step backwards, or a provider or OS holding the PUT. The 10-minute thaw uses each reader's own clock against the re-keyer's timestamp, so a skew of 10 minutes or more makes a fresh freeze "abandoned" at once. A re-keyer whose clock runs *ahead* blocks every push for the length of the skew after it dies; that part only affects availability.
- **Attack (honest provider):** the sequence is:
  1. A freezes and passes its check. Then its keyring PUT is delayed: suspend, held request, or simply B's clock running ahead.
  2. B thaws and commits `a.md` v2 over the freeze in epoch N.
  3. B re-reads the keyring, which is still N, keeps its commit and **deletes the v1 blob**.
  4. A's keyring lands, carrying the frozen digest with v1.
- **Result in the test:**
  - **The vault (epoch N+1) references a deleted blob.** A new device C loops on BlobMissing (`retries: 8, incomplete: true, files: []`), so `a.md` is gone for everyone without a local copy.
  - **B's next round throws** `RollbackError … same counter 4 (fork)`, permanently.
- **Test:** `rr12/t4-thaw-race.test.ts` FAILs. B's clock is +11 min, and B syncs inside A's `put(KEYRING)`.
- **Fix:**
  - **Serialize the thaw on the keyring:** a device that thaws first does a same-epoch CAS write on the keyring (seal `abortedFreeze: <frozen digest>`, with `rev+1` per RR-2). A's keyring CAS then fails if anybody thawed, and the 5-minute guard is no longer load-bearing.
  - **Delay GC after a thaw:** don't GC the blobs superseded by a commit written over a freeze until a later round has confirmed the keyring epoch.
  - **Bound the clock:** clamp `frozen.at` against the reader's clock, so a timestamp in the future counts as "now".

## RR-5 (medium, partly inherent): an unanchored device is rolled back to the pre-revocation epoch

- **Where:**
  - `engine.ts:144-196`: `unlockVault` has no epoch anchor.
  - `engine.ts:319`: a fresh state gives `seenEpoch = keys.epoch`.
  - `engine.ts:382`: `rekey` doesn't require a verified freshness.
- **Attack:** the provider colludes with the revoked phone. It serves a new laptop that unlocks with the passphrase (unpaired) the epoch-1 keyring and the pre-freeze epoch-1 manifest. Then:
  - The laptop syncs at epoch 1, and its new note is readable by the phone.
  - When the provider hides A's epoch-2 manifest, the laptop's re-key wraps the phone again (`laptop's re-key wraps for: ['phone']`).
- A paired device is protected, because the pairing anchor's counter is higher.
- **Test:** `rr12/t5-fresh-rollback.test.ts` FAILs: `revoked phone sees new.md: "written after the phone was revoked"`.
- **Fix:**
  - Refuse `rekey()`/`enrollDevice` while `freshness === "unverified"`.
  - Put the keyring epoch and keyring digest in pairing codes.
  - Show "this device can't verify it has the latest keys" on a passphrase-only join.
  - Correct spec §9: replay is detected only for devices that have an anchor.

## RR-6 (low): `.prev` outlives the passphrase change

- **Where:**
  - `engine.ts:189-193`: the old-passphrase fallback runs whenever `ring.file.header` exists and the stored header differs from it.
  - `keyring.ts:354`: the keyring of N+1 keeps `header` for the whole epoch. Step 3 (`engine.ts:443-447`) deletes `.prev` but never clears it.
- **Attack:** after the change has completed, the provider restores the old header and its saved copy of `.prev`, and the old passphrase opens epoch N again (`old passphrase opens epoch: 1`). The old passphrase still never reaches N+1, and a device opened this way can't sync (its refresh fails at N+1). The exposure is therefore limited to epoch-N data the old-passphrase holder already had. It does contradict spec §5 ("only while a passphrase change writes its header").
- **Test:** `rr12/t6-prev-after-change.test.ts` FAILs.
- **Fix:** don't put a `.prev` copy at the provider at all. The old passphrase only needs to open N while the header is missing, and the re-keyer can instead seal S_N under the *old* wrap key inside the new keyring, with an expiry. Or accept the path, document it, and refuse to `sync()` with keys from `.prev`.

## RR-7 (medium, from reading): CAS on real providers (origin/feat/e2ee-sync-providers)

The re-key's atomicity now rests on three conditional writes: the freeze (If-Match), the keyring (If-Match, or If-None-Match for the first one) and the new manifest (If-None-Match).
- **WebDAV** (`providers/webdav.ts:67-78`): `probe()` checks only that ETags exist, never that a stale `If-Match` / `If-None-Match` gets a 412. Servers that don't evaluate preconditions on PUT accept every write. nginx's dav module is the usual suspect; verify it. `normEtag` (`:36`) strips `W/` and sends a weak tag as strong in If-Match. A compliant server must then fail it (RFC 9110 strong comparison), which costs liveness, not safety.
- **S3** (`providers/s3.ts:66-71`): probes If-Match but not If-None-Match, which protects the first keyring, step 4, the header and blobs.
- **Drive** (`providers/gdrive.ts:8-16`, `:149-156`): create-only is look → create → look. That is not atomic, and it depends on the listing being consistent; the file says so itself.
- **Drive ETags in the freeze guard:** `engine.ts:433` compares the ETag returned by the media `PATCH` (`fields=id`) with the ETag from a later metadata `GET` (`fields=id,headRevisionId`). Google API ETags are per representation. If they differ, every re-key aborts with `PreconditionFailedError`, and revocation becomes impossible on Drive. This is untested against real Drive.
- **Dropbox:** rev-based update and `add` are atomic, so it is fine.
- **Fix:**
  - Probe both conditions on every provider; WebDAV needs a stale If-Match and a second If-None-Match:* PUT, both answered with 412.
  - In the re-key guard, compare the frozen manifest's **decrypted digest** after a fresh `get`, not ETag strings.
  - RR-2's same-epoch check turns any remaining CAS failure into a loud fork error instead of silent divergence.

## RR-8: the consequence when If-Match is ignored (confirmed)

- **Test:** `rr12/t8-cas-fork.test.ts` races A (revoke phone) against B (enroll laptop) at epoch 1.
  - **With real CAS (control):** B's commit is refused (`PreconditionFailedError`), and the phone has no wrap. PASS.
  - **With If-Match ignored:** both commit epoch 2. B's keyring wins (`B wraps ['phone','laptop']`), and the revoked phone gets the new secret. A stays at "epoch 2" with its own secret, and its next sync fails only with a generic `DecryptError`. FAIL.
- **Fix:** RR-2 and RR-7.

## RR-9 (low): spec, Python reader and TS disagree in places

- **Enrollment check:**
  - `scripts/sync-protocol/check_vectors.py:105-107` compares the sealed entry with the plaintext recipient. TS (`keyring.ts:223`) only checks the id is present.
  - Python never checks `revoked`, which spec §5 requires ("not in `revoked`").
- **Python accepts any manifest protocol** (`:114`), so a frozen protocol-2 manifest reads as normal, whereas spec §4 says protocol-1 readers refuse it. It also doesn't check the manifest's `vaultId`.
- **Pairing:** the pairing check derives the key from the passphrase master (epoch 0). For epoch ≥ 1, TS uses the epoch key (`keys.ts` epochKeys), and the only pairing vector is for the epoch-0 vault, so the two would disagree at epoch ≥ 1. The spec's key table puts pairing under the epoch secret.
- **Missing vectors:** frozen manifest, legacy keyring, pending-header keyring, `.prev`, `carry`.
- **Spec gaps:**
  - §5 has no rule for a different keyring at the same epoch (RR-2).
  - §9 says a replay is detected "through … the keyring epoch". That holds only for anchored devices (RR-5) and not for same-epoch replays (RR-1b).
