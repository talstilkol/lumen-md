## #473 (journalist mode), b4e212df6

**RR6-473-1: FIXED for what the tree pass models.**
- `treeInertCloses` walks micromark's events and keeps the HTML element stack. Its pops are conservative: it pops only when the top of the stack matches.
- The "both passes must agree" rule only ever adds `inert`.
- I checked whether one pass can error into a leak:
  - `events()`/`rawNodes()` throwing makes every close inert.
  - A throw in the main loop (outside the try) propagates out of `redactMarks`, so `prepareForExport` throws. No caller falls back to the raw text: `exportReady.ts`, `publish/site.ts:288`, `cli/publish.ts:412`, `cli/convert.ts:102,149` and `sync/publish.ts:228` all fail closed.
  - The tree pass's "close turned into an open" (`host.close = false`) only raises the depth in `removeRedacted`. I traced the case where the text pass then marks that open inert: it happens only while an outer passage is open in `removeRedacted` too, so the removal still runs on.
  - The fuzz below had 0 export errors.

The tree pass reads the note **as written and in source order**. The preview reads neither. That gives two new leak classes.

### RR8-473-1 (MEDIUM, confirmed in Chromium): CriticMarkup changes the text the preview parses

**Where:**
- `src/renderer/pipeline.ts:315-318`. The preview parses `prepareCriticMarkup(note)`.
- `src/renderer/criticMarkup.ts:76`. That swaps every delimiter of a suggestion (`{>>`, `<<}`, `~>`, `{~~`, …) for **one** private-use character.
- `src/lib/redactionTree.ts:182` (`events(text)`) and `redaction.ts:87-95`. Both export passes parse the raw note.
- The comment at `redactionTree.ts:25-26` ("CriticMarkup only swaps its delimiters … safe") is wrong. The `>` inside `{>>` and `~>` ends a tag for the export but not for the preview.

**Scenario** (`r473-critic.test.ts` K1):

```
Interview notes.

<redact>
Source: Dana Levi <span title={>>check<<} </redact> Yossi Cohen, 054-0000000

Met at the cafe on Herzl street.
```

- **Export:** `<span title={>` is a tag, so `</redact>` closes. The export is `█████ Yossi Cohen, 054-0000000 …` and keeps everything after.
- **Preview:** the span's attributes run on over a private-use character, and `</redact` becomes an attribute name. The passage never closes, so Yossi Cohen and every later block are shaded.

**Tests** (preview: the worktree's `prepareCriticMarkup` → micromark with the tree pass's extensions → Chromium's DOMParser; export: `exportReadyText`):
- K1 FAILS: Z2Z and Z3Z are kept.
- K2 (`{~~a~>b~~}`) FAILS.
- K3 (inside `<div>`) FAILS.
- The control K0 (the same note without the comment) passes.

**Reach:**
- Every export reads `exportReadyText` or `prepareForExport`: DOCX (`exportDocx.ts:547`), HTML (`exportHtml.ts:103`), PDF and print (`PrintExport.tsx:24`), MD and the other formats (`commands/domains/export.ts`), publish (`sync/publish.ts:228`), the site (`publish/site.ts:288`) and the CLI. One leak in that text is a leak in all of them.
- It needs a suggestion inside an unquoted attribute of a tag that runs into the close. Natural cases are rare. A co-editor (live share, classroom) can write it on purpose: the author keeps seeing the shading while the export publishes the names.
- The incremental preview isn't involved: `canRenderInBlocks` sends CriticMarkup notes to the full pipeline.

**Fix:**
- Run both passes on `prepareCriticMarkup(text)`, with an offset map back to the note.
- Or, failing closed: treat as inert any close that has a CriticMarkup delimiter between it and its passage's open.
- Add `prepareCriticMarkup` to the PR's fuzz oracle.

## #469 (collab relay, free), b3846f493

- **RR6-469-1: FIXED.**
  - `Quota.today()` never goes back, and callers pass ids, not a day.
  - Q2 passes.
  - V5 runs instance A with its clock 2 days ahead, then instance B with the right clock. B keeps A's day and gives one address 20 of 25.
  - DO clocks aren't attacker-controlled. A forward skew only resets the counts early once.
- **RR6-469-2: fixed against passive filler** (Q3 passes), **not against an attacker** (RR8-469-1 and -2).

The tests drive the real `CollabRoom`, `Quota` and `/token` with a fake relay. Every room has a DO id, and `env.ROOMS` reaches it, so `evict()` runs for real. Limits are scaled down (100,000 bytes, 200 rooms).

### RR8-469-1 (MEDIUM, confirmed): a refused new room evicts up to 8 stored rooms, for free

**Where:**
- `worker.mjs:525`. `evictFor` runs before the real `admit`, whenever the store is full and the caller passes the other limits.
- If the store is still full afterwards, the attempt is refused at `roomQuota.mjs:161`, before `rooms` or any bucket is counted.
- `evictionOrder` takes the smallest rooms first, which are ordinary notes.
- Protection is self-granted: any reconnect more than an hour after the last one calls `joined` (`worker.mjs:240`).

**Scenario:**
1. The attacker fills the bytes with big rooms (a room may hold 4 MB). One of them grows past the cap, and the attacker reconnects to each so that they are protected.
2. From one address it keeps opening new rooms. Each attempt is refused, and each deletes 8 other people's rooms.

**Answer to the question "Can eviction be abused to evict a victim's room?":** yes. Knowing the room's id doesn't help, and isn't needed: every unprotected room goes. A room that nobody rejoined in 14 days is gone, and its devices recreate it only if they still hold it.

**Test:** V1 FAILS. 5 refused attempts from one address deleted **30 of 30** victims' rooms, with 0 rooms admitted and today's count 44 → 44.

**Fix:**
- Evict only for an admitted room. Count the attempt.
- Free only the bytes that room needs, at most one room per admitted room.
- Prefer the asking owner's own rooms, or the largest.

### RR8-469-2 (MEDIUM, confirmed): idle sockets make every eviction fail, so the 90-day DoS is back

**Where:**
- `worker.mjs:365`. `evict()` refuses while **any** socket is open, including one that never authenticated. Nothing times those out.
- `evictFor` stops after 8 tries (`:546`), and a refusal costs a try.

**Scenario:**
1. The attacker stores 8 rooms of 1 byte each and leaves one hibernated, unauthenticated socket in each.
2. It fills the rest of the store.
3. Every eviction tries those 8 rooms first, all 8 refuse, and the loop stops.
4. Every new room on the public server is refused for as long as the attacker keeps the sockets open.

**Test:** V2 FAILS. A new user was refused at 100,008/100,000 bytes, and the 10 evictable legitimate rooms were never tried.

**Fix:**
- Count only authenticated sockets as "in use".
- Don't spend a try on a refusal; sort refusers to the end.
- Time out sockets that don't authenticate within N seconds.

### RR8-469-3 (LOW, confirmed): the owner lives only in memory

- **Where:** `worker.mjs:533` (`pending.set`) and `:569`. A Quota that restarts or is evicted from memory between `admit` and the first `saved` stores the room with owner `null`. `COLLAB_STORED_ROOMS_PER_ADDRESS` never counts such a room.
- **Scenario:** the attacker delays its first write past the Quota's idle eviction (or a deploy).
- **Test:** V3 FAILS. One address stored **80 rooms** in 4 days against a cap of 50, and every record has a null owner.
- **Fix:** persist the owner with the admission, or have the room pass its ids to `saved()`.

### RR8-469-4 (LOW, confirmed): no stored-room cap per /48

- The stored cap is per IPv4 address or /64. One /48 rotates /64s and stores 80 new rooms a day without limit.
- **Test:** V4 FAILS: 240 rooms in 3 days.
- **Fix:** also cap stored rooms per /48, with a second owner value from the `p:` id.

### RR8-469-5 (INFO)

- **Grinding the 20-bit owner:** impossible. It is an HMAC under COLLAB_TOKEN_SECRET (`roomQuota.mjs:125`), so it can't be ground or aimed at a victim.
- **Collisions:** an attacker who fills its own owner values blocks about 4,000 IPv4 addresses per value, at random. That is negligible.
- **Faking "rejoin":** nothing to fake. Any reconnect counts (`:240`), as the PR's "residual risk" says. Combined with RR8-469-1 and -2, though, that self-protection is what makes the attacks cheap.
- **Pre-existing, noted:** 50 unauthenticated sockets fill any room whose name is known (`MAX_PEERS`, `:317`).

## #451 (airplane mode), e7392e6e7

- **RR6-451-1, -2 and -3: FIXED.** `r451-escapes` passes 9/9.

### RR8-451-1 (LOW, confirmed in Chromium, latent): frames that `guardFrames` never decides

**Where:** `airplane.ts:365-430`. The guard covers property and `setAttribute` writes only.

**Escapes:**
- **W1:** a frame made by `innerHTML`.
- **W6:** a frame written with `document.write` into an unsandboxed same-origin `about:blank` frame (another window's prototypes).
- **W10:** `src` first, then `setAttributeNS(null,"sandbox",…)`.

Each keeps `allow-popups`. Its popup sends 12–13 requests after the switch and is not recorded: `trackOpen` sees only the app's own `window.open`.

**Reach:** no app path does this today. The sanitizers forbid iframes, and nothing writes into frames. But `airplaneCertificate.ts:33` states that "no frame gets allow-popups".

**Not reachable:**
- `<portal>` doesn't exist in this Chromium.
- `new FencedFrameConfig(url)` throws "Illegal constructor" (W9), and fenced frames need an unsandboxed embedder anyway.

**Embed service workers:**
- A known provider's service worker is the residual risk the certificate states.
- Any other site loses allow-same-origin, which E8 confirms.

**Fix:**
- Also wrap `setAttributeNS`, `setAttributeNode` and `Attr.value`.
- At the switch, count popups as possible for frames whose sandbox has `allow-popups`.
- Word the certificate "frames the app creates".

### RR8-451-2 (LOW, confirmed in Chromium, functional)

- **R1:**
  - EmbedBlock and the raw-HTML sanitizer dropped `allow-popups` **always**, not only while the switch is on.
  - A provider's "Watch on YouTube" link (`target=_blank`) now does nothing; the same goes for "Open in Spotify" and tweet links.
  - EmbedBlock's header has its own "open" link.
- **R2:**
  - `EMBED_ORIGINS` (`airplane.ts:321`) omits origins that `public/_headers` frame-src allows: `www.youtube.com`, `maps.google.com`, `www.reddit.com` and `gist.github.com`.
  - A pasted `<iframe src="https://www.youtube.com/embed/…">` (what YouTube's Share > Embed gives) now runs with `sandbox="allow-scripts allow-presentation"`.
  - `localStorage` throws SecurityError there, origin null. YouTube's player is likely to break; that was not run against the real site.
- **Fix:**
  - Make `EMBED_ORIGINS` and frame-src one list.
  - Keep `allow-popups` while the switch is off: frames made then are blanked at the switch, and popups could be counted as possible.

### RR8-451-3 (INFO)

`rehypeSanitizeRaw`'s DROP_ELEMENTS has `portal` but not `fencedframe`. A fenced frame is inert without script; add it anyway.
