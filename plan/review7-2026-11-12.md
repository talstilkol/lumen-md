### F1: labels and versions (downgrade)

`pairing.ts:171-208` computes `HMAC(pairing_N, "lumen-pair/<kind>/<v>\0" ‖ body)`. The body carries `kind`, the reader requires exactly that kind's field set, and the answer carries `request = sha256(request text)`.

`rr7/r7-3-pairing-downgrade.test.ts` tests this two ways:

**(a) A 63-cell matrix.**
- Inputs: the 3 genuine messages × 7 prefixes (the 3 current ones and the 4 older ones) × 2 readers.
- Only the 3 genuine messages in their own slot are accepted.
- Every other cell is refused, either as "older build" or because the MAC fails.

**(b)/(c) Messages carrying a *valid* MAC in the 7807f3bf28 format** (no label, old body) under the real pairing key.
- They are refused under both the old prefixes (`lumen-pair:2:`, `lumen-pair-request:1:`) and the new ones.
- A new-shape body under a label-less MAC is also refused.

Two arguments cover what the tests can't:
- **Can an old-build reader be fed a new message?** Its MAC input would be `json`, but a new tag covers `"lumen-pair/…"‖json`, which isn't JSON. A new message can't verify on an old build, and an old one can't verify on a new build.
- **Mixed builds:** old builds in the field remain reflection-vulnerable among themselves. They exist only on pre-release installs. Info.

### Dropped marker: a spoofing vector?

**At unlock** (`unlockWithDevice`, `keyring.ts:353`), the marker is unauthenticated. The provider can turn any `RevokedError` into `DroppedFromVaultError`, or strip a genuine marker to get the reverse.
- Only the message changes. Re-pairing goes through an honest device's `enroll`, which refuses revoked ids and keys.
- No UI path acts destructively on either error (`ui/errorText.ts:26-27` maps them to text only).
- This is acceptable and documented.

**On the authenticated path** (`engine.ts` refresh → `verifyDropped`), the check can be beaten by replaying an old genuine marker: **G2**.

### KeyChangeInProgressError as a denial-of-service lever

| Who | Can they keep the vault from re-keying? |
|---|---|
| **The provider alone** | **No new lever.** It can't seal a frozen manifest. Serving an old one is a rollback (`RollbackError`) or is listed in `aborted`. A provider can always refuse writes, and that refusal is loud. |
| **A device already revoked** | **No.** It lacks the current epoch's secret, so it can't seal a manifest under the current label. |
| **The device about to be revoked** (a stolen phone with its storage login) | **Yes: G1.** This is the case revocation exists for. |

### dropDevices consent bypass

None found. `rr7-5 (a)`:
- `rekey({revoke:["tablet"]})` → `DropDevicesRequiredError ["phone"]`.
- `rekey({enroll:{laptop}})` → `["phone","tablet"]`.
- A passphrase change → `["phone","tablet"]`.

Both automatic re-key paths, `enforceRevocations` and `reapplyRevocation`, are guarded by `freshness !== "unverified"` and never drop.

The list the user consents to is the sealed list of the keyring the unverified device sees, so a stale view can under-report it. That is inherent to being unverified, and the device can't make it worse.

Note that a passphrase change from an unverified device also needs `dropDevices`. That is correct (it is a re-key), but the UI must word it that way.

### F5: "an unverifiable header counts as Argon2id"

`rr7-5 (b)`, PBKDF2 vault, header garbled for the one read:
- The new header is Argon2id with production defaults, and the new passphrase opens the vault.
- This can only ever be an *upgrade*:
  - the Argon2id parameters come from `rekeyHeader`'s defaults, not from the stored header;
  - the header MAC covers `kdf`, so iterations can't be lowered;
  - an older genuine header is MAC'd under another passphrase's key, so it doesn't verify.
- A device-key device has no header key. `headerMacValid` then fails closed, which again means Argon2id.
- The only cost would be a pre-W1.7 build that can't run Argon2id. That is pre-release only. Info.

### The revoked-devices list keyed from S0

These are the three questions from the brief.

**What if epoch 0 is compromised?**
- S0 is never rotated, and every device and passphrase that ever had access holds it, including the revoked phone.
- So the MAC gives no integrity against those parties. It doesn't need to: `revokedHere` lives only in the local state store, which they can't write.
- S0 also keys the opaque names. That is pre-existing: a revoked device can still compute file-name HMACs.

**Can it be lost or rolled back?** Yes. `rr7-5 (c)`:
- A state without `revokedHere` (a reinstall, a restored backup, cleared storage) silently accepts a keyring that lets the phone back in.
- The same keyring is caught with the list present (`KeyringForkError ["phone"]`).
- The MAC detects change, not deletion. That is **G5** (low): it only needs a CAS-lie sibling to matter, and the sealed `revoked` list plus N2's read-back still apply.

**Wedge risk:** if the list ever fails to verify (for example, a future reset path that changed S0), `revokedHere()` throws `KeyringForkError` on every refresh, with no way out.

### cancelPairing races

`rr7-4`:

**(a) The answer is used after cancel and revoke: G4, inherent.**
- A answers, the user cancels, then revokes the phone (epoch 2).
- The answer, entered on a laptop that the storage keeps on the epoch-1 view, pairs the laptop. It uploads, and the phone reads `new.md`.
- The engine's doc and `e2ee.pair.cancelled` say exactly this ("Don't use that answer or code on the other device"), and no client-side check can see it: the laptop only sees the provider.

**(b) pairingCode() runs outside `exclusive` (engine.ts:985): G3.**
- A code made while a revocation is in flight vouches for epoch 1. The in-flight re-key checked the lock before the code existed.
- A stale laptop pairs with the code and re-keys for `["phone"]`.
- This is pre-existing, not caused by cancelPairing. `cancelPairing` itself runs under `exclusive` and is race-free with `answerPairing` and `rekey`.

## 4. New findings

### G1 — MEDIUM (regression) — the device being revoked blocks its own revocation and every passphrase change

- **Where:**
  - `src/sync/e2ee/engine.ts:787-793`, in `rekeyNow`'s freeze loop. `frozenSeen` is reset whenever `remoteDigest` changes.
  - The same per-digest reset in `round()` at `engine.ts:1344-1356` (pre-existing since RR-4).
- **Scenario:**
  1. A phone is stolen. It holds S1 and the WebDAV login.
  2. Every 9 minutes it writes a frozen successor of the epoch-1 manifest, sealed with S1, with `If-Match`, which an honest server accepts. `by` can be any string.
  3. A's `rekey({revoke:["phone"]})` sees a new digest each time, restarts the 10-minute wait, and throws `KeyChangeInProgressError` ("10 minutes at most"), for ever.
  4. A passphrase change goes through `rekeyNow` too and is blocked the same way.
  5. Every round returns `rekeyPending` with nothing uploaded.
- **Impact:**
  - The vault can't be re-keyed or synced while the phone keeps doing this.
  - New notes aren't leaked, because rounds hold their uploads. But the security action the user needs is impossible from the client.
  - The only escape is to cut the phone's storage login or move the vault.
- **Test:** `rr7/r7-1-freeze-lockout.test.ts`.
  - On all three heads it gives 1/2. The control passes (one stale freeze: A revokes after the TTL). The lockout case FAILs:
    ```
    KeyChangeInProgressError ×6 over 54 minutes | passphrase change: KeyChangeInProgressError | A's sync: rekeyPending=true uploaded=0 | phone still unwraps the live epoch: true
    ```
  - At 7807f3bf28 (`w-rr5-399`), the same lockout case gives `epoch 2 | passphrase change: epoch 3`. That run's control fails only because `KeyChangeInProgressError` doesn't exist there.
- **Fix:**
  - Bound the wait per re-key *intent*, not per digest. Persist `rekeyBlockedSince` at the first `KeyChangeInProgressError`. Once `now - rekeyBlockedSince ≥ FREEZE_TTL_MS` (this device's clock), freeze over whatever foreign freeze is there. Clear it on commit.
  - In `round()`, keep `frozenSeen.at` while consecutive manifests are foreign freezes; reset it only on an unfrozen manifest or an epoch change.
  - t8 stays defended: an honest re-keyer commits within seconds, far inside the 10 minutes.
  - Add rr7-1 as a regression test.

### G2 — LOW — a replayed genuine dropped marker turns a revocation into "pair again"

- **Where:** `src/sync/e2ee/keyring.ts`.
  - `verifyDropped` / `markerValid` accept any marker that lists the device and whose MAC the device's older secret reproduces.
  - The marker is outside the digest, so the provider can carry an old one forward.
- **Scenario:**
  1. The tablet is dropped at epoch 2 (marker M2).
  2. It is re-enrolled at epoch 2.
  3. It is then really revoked at epoch 3. The marker is correctly not carried.
  4. The provider puts M2 back.
  5. The tablet's round now throws `DroppedFromVaultError` ("it wasn't removed… pair it again or unlock it with the passphrase") instead of `RevokedError`.
- **Test:** `rr7/r7-2-dropped-marker-replay.test.ts` FAILs:
  ```
  honest round: RevokedError | with the old marker put back: DroppedFromVaultError
  ```
- **Impact:** a message only. Re-enrolling the same id or key is refused. It misleads a user into re-pairing a device someone else removed.
- **Fix:** in `verifyDropped`, accept a marker only if `m.epoch === keys.epoch + 1`, the first epoch this device doesn't hold. Drop a device's markers when it is enrolled again.

### G3 — LOW (pre-existing) — a one-way code issued during an in-flight revocation

- **Where:** `src/sync/e2ee/engine.ts:985`. `pairingCode()` isn't wrapped in `this.exclusive`, and `rekeyNow` checks `pairingUntil` only once, at `:754`.
- **Scenario:**
  1. The provider stalls A's revocation at the keyring PUT.
  2. The user, waiting, shows a pairing code. It vouches for epoch 1.
  3. The revocation commits epoch 2.
  4. A laptop kept on the epoch-1 view pairs with the code within its 2 minutes, then re-keys for `["phone"]`.
- **Test:** `rr7/r7-4-pairing-races.test.ts` (b) FAILs:
  ```
  laptop (epoch-1 view): paired | laptop re-key wraps: ["phone"] | phone unwraps: true
  ```
- **Fix:** `pairingCode()` → `return this.exclusive(async () => …)`, and re-check `checkNoPairingPending()` just before the keyring commit.
- **Reach:** latent. #291 has no revoke UI.

### G4 — INFO (inherent; accepted) — an answer or code used after `cancelPairing`

- **Test:** `rr7-4` (a) FAILs as expected:
  ```
  laptop with the old answer: paired | revoked phone reads: ["a.md","new.md"]
  ```
- **Why it is inherent:** a given-out snapshot can't be revoked from the client.
- **Mitigation in place:** `e2ee.pair.cancelled` warns. The UI should keep that warning visible next to the revocation result.

### G5 — LOW — `revokedHere` detects change, not loss

- **Where:**
  - `engine.ts` `revokedHere()`: `if (!r) return []`.
  - The key comes from S0 (`keys.ts` `revokedHereKey`).
- **Test:** `rr7-5` (c), described in section 2.
- **Fix:** additionally require monotonicity of the sealed list. The adopted keyring's sealed `revoked` must be a superset of the one this device anchored, so keep `revoked` ids in `RingInfo`/the anchor. That needs no local list and survives a reinstall that re-pairs. Also give a list that fails to verify a recovery path ("re-check with a trusted device") rather than a permanent `KeyringForkError`.
