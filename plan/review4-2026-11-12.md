## Disputed test: `rr2/r451-runner-open-before.mjs`

**Decision: lane R is right. The original tests the browser, not the app, and no app fix could make it pass. Lane R's variant tests the same threat faithfully, so I accept it in place of the original.**

- **The original.** Its `switchOn` is a hand-written model of the pre-fix `enableAirplaneMode`: it inserts the `<meta>` and does nothing else. It never loads any of the app's code. As evidence for RR2-451-2 against `81728f474`, it was valid: that is exactly what the old switch did. As a regression test, it can only ever show the browser fact that a parent's `<meta>` CSP doesn't reach a child that is already running. It still fails on the new head (7 requests after the switch), and it would fail against any fix.
- **The variant** (`R/r2/t451/r451-runner-open-before.real.mjs`). It bundles the worktree's real `installAirplaneMode` and `enableAirplaneMode` with esbuild. The runner keeps the same header CSP, the same 200 ms image loop, the same 50 ms grace and the same control request from the app window. It renames `/runner.html` to `/playground-runner.html`, which is the path `PlaygroundBlock.tsx:39` really uses, and which the fix's selector needs. It is also stricter, because it requires exactly one `in-flight` frame record.
- **It discriminates.** It PASSES on `8f521a5fa` (0 requests after the switch, 1 frame recorded). It FAILS on the pre-fix `81728f474` (7 requests, 0 recorded); I ran it against `/home/claude/w-rr2-451`.
- **What it doesn't cover is a separate gap, not a weakening.** The variant's frame has a runner URL by construction. Frames without a runner URL are not stopped. That isn't the threat RR2-451-2 described, so I filed it as a new finding (RR4-451-1) with its own test.

### RR4-483-1 (MEDIUM, confirmed): a client can choose its own address

**Where:**
- `sync-server/vault-relay.js:280-293` (#488: `:315-328`). In the default `auto` mode:
  - `Fly-Client-IP` is trusted from **any private peer** (`:290`);
  - the last `X-Forwarded-For` hop is trusted from any loopback or private peer (`:292`).
- `sync-server/server.js:64-71`, which the relay now uses when it is mounted (`:145`). With `SIGNAL_TRUST_PROXY=1`, it reads `Fly-Client-IP` first and then the **first** `X-Forwarded-For` hop.

**Scenarios:**
- **P2, the school relay of `classroom.md`.** The docs say "A school can run that relay on its own network: `VAULT_RELAY_DIR=… node sync-server/vault-relay.js`". There, every laptop is a private peer, so its own `Fly-Client-IP` header is believed. One laptop (`10.20.0.66`) opened **40 spaces against a limit of 5**, so no daily limit holds.
- **P3, targeted.** A student writes a classmate's address (`Fly-Client-IP: 10.20.0.23`) and spends that address's 5 spaces. The classmate's first submission then gets `429 {"error":"new spaces today"}`. The per-minute rate limit can be turned on a classmate the same way.
- **P4, standalone behind nginx on a load balancer at 10.0.0.2.** Nginx passes the client's own `Fly-Client-IP` through by default, so one client opened 40 spaces. The code comment says "a proxy other than Fly's must drop a client's own Fly-Client-IP", but no config enforces it, and I didn't find it said in the user docs.
- **P5, mounted in `server.js` with `SIGNAL_TRUST_PROXY=1` behind nginx.** `server.js`'s own comment names nginx for this setting. 20 of 20 spaces opened, both with a forged `Fly-Client-IP` and with a forged first `X-Forwarded-For` hop.

**Test:** `rr4/r483-proxy.test.mjs`. P2, P3, P4 and P5 FAIL on #483 and #488; P1 (the control) passes.

**Fix:**
- Trust no header by default.
- `VAULT_RELAY_TRUST_PROXY=fly` trusts `Fly-Client-IP` only. Accept it only from Fly's 6PN range (`fdaa::/16`), or only when `FLY_APP_NAME` is set.
- `VAULT_RELAY_TRUST_PROXY=<CIDR list>`, for an explicit proxy list: take the right-most `X-Forwarded-For` hop that is not one of the proxies.
- Give `server.js`'s `clientIp` the same rule: the last hop, not the first, and `Fly-Client-IP` only on Fly.
- Add the rule to `two-clicks.md` and `classroom.md`.

### RR4-483-2 (LOW, confirmed by simulating the relay's own sketch): saturating the sketch blocks new addresses

**Where:** `vault-relay.js:256`, `sketch(1<<16, 4)`, used for new spaces per day.

**Over-counting against shared addresses (schools): not a real problem at normal load.**
- The cells come from a daily HMAC key, so nobody can aim at a given address.
- Collisions are negligible: at 100,000 new spaces a day, 0.49 % of new addresses are refused.
- What does hurt a school on the public relay is the per-address limit itself: one NAT address gets 5 new spaces a day for the whole school. That is documented, and it can only be raised on a relay the school runs itself, where RR4-483-1 applies.

**Saturation:** an attacker controlling many /64s fills the sketch.
- 65,536 /64s (one free /48 tunnel), each at its 5 spaces a day, means 327,680 tiny spaces (about 1.3 GB of block charge). Then **16 %** of new addresses are refused their first space for the rest of the day.
- 131,072 /64s means **55 %**.
- Both stay under the 20 GiB global cap.

**Test:** `rr4/r483-proxy.test.mjs` P6 (informational).

**Fix:**
- Also count IPv6 by /48 (and /56), with their own daily limits.
- Size the new-space sketch for the expected load.
- Consider turning the PoW on by default for the public relay.

### RR4-469-1 (LOW, confirmed with lane R's fake relay): whoever authenticates first binds the room

**Where:** `edge-workers/collab/worker.mjs:168`, `this.verifier ??= v`. The first authenticated token binds the room whatever proof it carries. The binding is persisted with the first save (`:220`).

**Scenario:**
- Someone who knows a room's name but not its password binds it first. They need a random 43-character "proof" and 18 bits of work.
- From then on, the owners' real proof is refused for good.
- The name can be known in advance in two cases:
  - a typed `#room=<name>` link (`readRoomFromHash` accepts any `[\w-]+`);
  - any room stored before this change, through the stated trust-on-first-use decision.
- App-made rooms are not exposed: their names are 128-bit random (`yjs.ts:163`), and the creator connects first.

**Race:** the attacker can't win the race for an app-made room, because they learn the name only after the creator has connected. They do win it for names known before the room is bound.

**Offline guessing:** nothing cheaper than before.
- The proof costs the same 200,000-iteration PBKDF2 as the room key (`encryption.ts:61`), so the verifier or the proof gives no cheaper test than the ciphertext the server already stores.
- Default passwords are 128-bit random (`makeRoomPassword`).
- One point: the server receives the proof itself, not only its hash. The proof is a bearer secret that lasts for the life of the room, and it lets its holder join and write. It does not let them read.

**Test:** `rr4/c469/r469-bind-race.mjs` B1 FAILS: the squatter joined, `verifier` was stored, and the owners were refused. It uses the real `worker.mjs` and `roomToken.mjs` with lane R's fake relay, corrected to pass the room name through; Yjs isn't available offline.

**Fix:**
- Refuse trust-on-first-use for rooms stored before the change: their owners re-create the room.
- Let a room accept a rebind only from a client that also presents a valid E2EE envelope already in the room. Alternatively, have the creator register the verifier with an owner secret at creation.

### RR4-451-1 (MEDIUM, confirmed in Chromium): frames other than the runners keep reaching other sites after the switch

**Where:** `src/privacy/airplane.ts:272`. `stopRunnerFrames` skips every frame whose `src` doesn't match `/-runner\.html/`.

**Frames that keep the policy they were created with:**
- **An HTML preview block with "allow scripts" on** (`HtmlPreviewBlock.tsx:141`, srcdoc, `sandbox="allow-scripts"`). A srcdoc document copies the parent's policy when it is created, so the `<meta>` added later doesn't reach it. The app's header CSP has `img-src … https:`.
- **A loaded embed** (`EmbedBlock.tsx:282`, a third-party page under its own policy).

**Scenario:** a live HTML demo with a timer, or an open video or tool embed, is on the page when the user turns airplane mode on. It keeps sending, and the certificate records nothing. Yet `enableAirplaneMode`'s doc comment says "everything is stopped from this moment", and `notCounted` speaks only of runner frames.

**Test:** `rr4/r451-preexisting-frames.mjs`. After the switch:
- runner: 0 requests (the control passes);
- HTML preview: **8** requests;
- embed: **7** requests;
- 1 frame recorded.

On `81728f474`, all three keep sending.

**Fix:**
- In `enableAirplaneMode`, blank every `iframe` in the document: set its `src` to `about:blank` and remove its `srcdoc`. Record each one as `in-flight`.
- Or have HtmlPreview, LiveCss and Embed unmount their frames while `airplaneFlagOn()`.
- State the scope in `counts` and `notCounted`.

### RR4-473-1 (LOW, confirmed): a closed locked note can be replaced by an envelope with its copied salt

**Where:** `src/storage/lockedNote.ts:207` accepts any well-formed envelope whose `kdf` (salt included) equals the current file's. Those KDF parameters are plaintext in the file itself.

**Scenario:** a tool, plugin or agent write copies the salt from `sources.md` and then does one of two things:
- **C1:** writes junk ciphertext. The note is destroyed with no error.
- **C2:** seals planted text under its own password, using the copied salt. The owner's password now fails with `WrongNotePasswordError`, and the writer's password opens `"my source is Y (planted)"`.

The PR text says "a forged envelope with a copied salt still cannot be opened by anyone else". That is not true: the forger can open it.

**Test:** `rr4/r473-copied-salt.test.ts`. C1 and C2 FAIL; C3 (the control: the note's own envelope) passes.

**Fix:**
- While a note is closed, accept only byte-identical text.
- Route sync pulls through an explicit allowance, as `allowPlainWrite` does. Alternatively, keep the replaced envelope in history, so it can be recovered.
- Correct the PR text.

### RR4-473-2 (LOW, confirmed): photos under other labels, and "plain" files, go out unread

**Where:**
- `src/lib/redaction.ts:195`: `DATA_IMAGE` matches only `data:image/(jpeg|jpg|png|webp)`.
- `src/lib/imageMetadata.ts:75`, `:409`: GIF, SVG, BMP and ICO are copied without being read.

**Scenario:**
- A note holds `data:image/heic`, `data:image/avif`, a JPEG labelled `image/gif`, or `application/octet-stream` (for example, from an imported HTML or Markdown file). It leaves both export doors, and Publish site, with its GPS. Browsers decode an image by its content, and WebKit draws HEIC.
- An SVG that embeds the original photo as a `data:` URL (Inkscape's "embed", diagram tools) is published with its GPS.

**Test:** `rr4/r473-inline-labels.test.ts`. 5 of 7 FAIL: heic, avif, gif-labelled JPEG, octet-stream, and the SVG.

**Fix:**
- Find every `data:` URL in image position, sniff its bytes, and clean or withhold it by content.
- In SVG, clean or withhold the embedded `data:` images.
- Treat an ICO's PNG frames as PNG.
